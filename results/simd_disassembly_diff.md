## preemphasis

Pre-emphasis then Hamming window. `y = x[i] - a*x[i-1]` is a two-tap stencil, so the vector body needs one unaligned load (p + i - 1) per four samples and cannot avoid it: the shifted stream genuinely starts one element earlier. The forward loads and both stores are aligned.

`16.000` -> `1.938` instructions per sample (8.26x fewer).

**preemph_scalar** (`.LBB1_2`, 16 instructions)

```asm

  shr rdx, 4
  mulx rdx, rdx, rsi
  imul rdx, rdx, -1600
  add rdx, rcx
  vmovss xmm3, dword ptr [rdx + 4*r11]   # xmm3 = mem[0],zero,zero,zero
  vcvtss2sd xmm3, xmm3, xmm3
  vsubsd xmm3, xmm3, xmm0
  vfmadd132sd xmm2, xmm3, xmm1        # xmm2 = (xmm2 * xmm1) + xmm3
  vmulsd xmm2, xmm2, qword ptr [r8 + 8*r11]
  vmovsd qword ptr [r9 + 8*r11], xmm2
  inc r11
  inc rax
  vmovapd xmm2, xmm3
  cmp r10, r11
  jne .LBB1_2
```

## What is still unaligned, and why

* `preemph_avx2`: 4 unaligned moves in the hot loop.
* `log_avx2`: 2 unaligned moves in the hot loop.

The pre-emphasis stencil reads `p[i-1]` while the window coefficient and the
output store advance at `i`. Making the shifted load aligned would mean either
shifting the whole frame by one element before the loop (an extra copy per
frame) or keeping a duplicated ring with a one-sample prefix. Neither is free,
and on this hardware the unaligned load is not the bottleneck, so the audit
records the count instead of hiding it.
